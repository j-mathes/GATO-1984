# Embedded data tables, repeating patterns and graphics data

Generated by [scan_data_tables.py](scan_data_tables.py). Scope: `DEMO.EXE` and `Gato1.exe` (the two programs with the game engine). Offsets are **file offsets**; `ds:` is the offset inside the BASIC data segment (file offset minus the data-segment base recovered from the string-literal descriptors). Thresholds and methods are at the top of the script.

## 0. Short answers

* **Trig/math tables: yes** - runtime MBF coefficient tables (SIN polynomial; ATN and EXP series in `Gato1.exe`) and pi-related constants (section 2). They belong to the BASIC runtime, not the game.
* **Game numeric constants: yes** - the literal pool also holds MBF numbers (129 in `DEMO.EXE`, 197 in `Gato1.exe`): angles such as 0.7854 and 5.4978, sprite/screen coordinates, limits such as 8000, 10000 and 25000 (section 2.3).
* **Map coordinates:** one `DATA` table of 12 x (x, y, size, aspect) values (section 4). The real island map is the external `MXP` file.
* **Morse code table: not found** in any encoding tried (section 6). The only Morse-like assets are two `PLAY` strings in `Gato1.exe`.
* **Raw CGA 2-bit bitmaps / GET-PUT blocks: none found.** Sprites are `DRAW` command strings (section 5) drawn at run time. The code that defines the CGA bitmap layout is documented in section 7.

### 2.4 Number-formatting tables (powers of ten and digit-count staircases)

Found by exact structure, not by name: a table of 64-bit little-endian integers descending from `10^18` (`00 00 64 a7 b3 b6 e0 0d`; 11 entries, down to `10^8`), followed by byte ramps that rise by 1 every ~3.32 entries (slope ~ log10(2) = 0.30103), i.e. a map from a binary exponent to a decimal digit count. The two ramps are adjacent and wrap from 0xff to 0x00, so they are one signed-byte ramp of 287 entries running from -30 to +56 (about floor(n x log10 2)). ## 7. CGA graphics: code signatures, byte tables, bitmap headers

### 7.1 Code that defines the bitmap layout

| signature | DEMO.EXE | Gato1.exe | meaning |
|---|---|---|---|
| CGA video segment load | 0xbe52, 0xbe75, 0xbf45, 0xc0f1, 0xc180, 0xc240 | 0x10f8e, 0x10fb1, 0x11081, 0x1122d, 0x112bc, 0x1137c | mov reg,0B800h: direct CGA frame-buffer access |
| CGA row address (y>>1)*80 + (y&1)*0x2000 | 0xbe90 | 0x10fcc | pixel address from Y: 80 bytes per row, +0x2000 for odd scan lines (interleaved CGA) |
| CGA 2bpp mask build (0xC0 >> 2*(x&3)) | 0xbec7 | 0x11003 | pixel mask for 320x200x4: 0xC0 shifted by 2*(x mod 4) |
| CGA 1bpp mask build (0x80 >> (x&7)) | 0xbeb4 | 0x10ff0 | pixel mask for 640x200x2 |
| pixel XOR write to frame buffer | 0xbe89, 0xc254 | 0x10fc5, 0x11390 | xor es:[bx],al - XOR drawing as used by PUT XOR / PSET |

These match the pixel routines at Gato1 0x10f8c-0x1100c (disassembled by hand): the **CGA interleaved layout**. Scan line `y` starts at `(y>>1)*80 + (y&1)*0x2000` from segment 0xB800; in 320x200 mode each byte holds 4 pixels of 2 bits (leftmost pixel in bits 7-6, mask `0xC0 >> 2*(x&3)`); 640x200 mode uses 1 bit per pixel. A mode byte in the data segment (DS:0x0087, bit 0 set = 1 bpp) selects between them. Any sprite captured with `GET` therefore has the header `[width in bits][height]` and rows padded to whole bytes.

The left-fill mask table sits at the end of the math-table zone in both programs; the right-fill, 2bpp-mask and colour-fill byte tables are *not* present as tables (the code builds those masks with shifts, see 7.1).

### 7.3 GET/PUT-style bitmap blocks

A `GET` array starts with `[width in bits][height]` followed by rows padded to whole bytes (320x200 mode: width bits = 2 x pixels). Every offset of each load module was tested for 8 <= width-bits <= 640 (even), 4 <= height <= 200, data neither mostly zero nor mostly printable; candidates were then scored by row-to-row similarity, since real images repeat bytes between adjacent rows.

* DEMO.EXE: 25 header-shaped candidates, 0 with row similarity >= 0.5 (best similarity 0.24 at 0x0eee4 (ds:0x36e4), zone DS-image: literal pool).
* Gato1.exe: 23 header-shaped candidates, 0 with row similarity >= 0.5 (best similarity 0.23 at 0x13bf4 (ds:0x32f4), zone DS-image: literal pool).

**Conclusion:** no embedded pre-rendered bitmap blocks. Header-shaped matches are statistical coincidences. In compiled BASIC a `GET` array is filled at run time from the screen after the sprite is drawn with `DRAW`, so the executables hold `DRAW` strings (section 5) and the `OBX` files hold the ship vectors. Pre-rendered blocks could only appear if the program `READ` them from `DATA` text; the only `DATA` text is the 48-number table in section 4.
