# GATO executable architecture

Generated by [map_executables.py](map_executables.py) from the binaries in `Original/` (the task text said `original_game/`; the folder is `Original/`). Full per-file string dumps are in [strings/](strings/); the earlier per-file reports are [exe_strings.txt](exe_strings.txt), [exe_comparison.txt](exe_comparison.txt) and its siblings.

## 1. Summary

```text
DOS prompt
   |  (only Gato.exe is started from DOS)
   v
GATO.EXE  title screen + menu  [1] play  [2] demo  [3] history  [4] exit
   |-- 1 / default --CHAIN "GATO1"  --> GATO1.EXE    (game; ends back at DOS)
   |-- 2           --CHAIN "DEMO"   --> DEMO.EXE     --CHAIN "GATO" --> GATO.EXE
   |-- 3           --CHAIN "HISTORY"--> HISTORY.EXE  --CHAIN "GATO" --> GATO.EXE
   `-- 4           --END--> DOS
```

* All four are **IBM BASIC Compiler** programs with the IBM runtime linked in; none is packed.
* `CHAIN` is implemented **inside the BASIC runtime** as an in-process EXE loader (FCB file I/O, manual relocation, `retf` into the new image). The executables never call DOS EXEC (INT 21h AH=4Bh).
* **No configuration state is handed over.** The launcher passes only the *choice of program*; the loader copies nothing but its own header/FCB buffer and the original PSP stays in place. The only persistent state shared by the game and the demo is the Captain's Log data file (`LOG1`).

## 3. Compiler and runtime

* Licence string `Licensed Material - Program Property of IBM` at `Gato.exe` 0x1016, `Gato1.exe` 0xd9a4, `DEMO.EXE` 0x88a8, `History.exe` 0x364.
* The decoded runtime error table is identical in all four (35 entries, highest error 72; no errors 73-76).
* No Microsoft, QuickBASIC, GW-BASIC/BASICA or C-runtime markers; machine code is far-call/`push bp` BASIC compiler output, not hand assembly or C.
* DOS API used by the runtime (INT 21h function number resolved from the preceding `mov ah`): 09h print string, 0Dh disk reset, 0Eh select disk, 0Fh open FCB, 10h close FCB, 11h find first, 12h find next, 13h delete FCB, 16h create FCB, 17h rename FCB, 19h get current disk, 1Ah set DTA, 27h random block read, 29h parse filename, 2Ah get date, 2Bh set date, 2Ch get time, 2Dh set time.
  Highest function number used: 2Dh. Handle-based file functions (3Ch, 3Dh, 3Eh, 3Fh, 40h, 41h, 42h, 43h, 4Bh, 4Ch) are never used; file I/O is FCB-based throughout. That matches a runtime written for DOS 1.x and the error table lacking the DOS 2 path errors.
  (5 INT 21h byte pairs could not be resolved: one is a shared wrapper whose caller sets AH, one is the operand of a `jmp far` in `DEMO.EXE`; none is a function above 2Dh or an EXEC.)
* Numbers are Microsoft Binary Format singles (e.g. the launcher compares the menu choice with the constants `00 00 00 82` = 2.0, `00 00 40 82` = 3.0, `00 00 00 83` = 4.0). MBF therefore exists inside the programs, but not in the scenario data files (those are plain text).
* **Exact version: not recoverable.** No version/release string exists; the evidence only supports "early IBM BASIC Compiler runtime, DOS 1.x-era". Anything finer (1.00 vs 1.10 vs 2.00) would need a known compiler build to compare against.

## 4. How GATO.EXE launches the others

### 4.1 No DOS EXEC

| file | INT 21h byte pairs (whole load module) | AH=4Bh calls | stray `B4 4B`-like byte patterns (not followed by INT 21h) |
|---|---:|---:|---|
| Gato.exe | 33 | 0 | 0x61a1 |
| Gato1.exe | 25 | 0 | 0x141bf |
| DEMO.EXE | 36 | 0 | 0xf46d |
| History.exe | 31 | 0 | 0x44f5 |

INT 21h AH=4Bh is never executed. Searched strings in all four binaries: `COMMON`, `CHAIN`, `CONFIG`, `.CFG`, `.TMP`, `.INI`, `.BAT`, `COMSPEC`, `COMMAND.COM`, `SYSTEM` -> no hits.

### 4.2 The CHAIN loader (found in the launcher, the demo and the history viewer)

| file | loader routine (file offset) | 'Error in EXE file' text | parse name (29h) | open FCB (0Fh) | read block (27h) | applies relocations | keeps original PSP | words copied |
|---|---|---|---|---|---|---|---|---|
| Gato.exe | 0x2767 | 0x28d1 | yes | yes | yes | yes | yes | 0x58, 0x20 |
| Gato1.exe | none | no | - | - | - | - | - | - |
| DEMO.EXE | 0xa912 | 0xaa7c | yes | yes | yes | yes | yes | 0x58, 0x20 |
| History.exe | 0x1bbf | 0x1d29 | yes | yes | yes | yes | yes | 0x58, 0x20 |

What the routine does (read from the disassembly of the launcher's copy at the offset above; the table shows the same DOS calls, relocation step and PSP hand-off were found in the other two copies):

1. Takes the BASIC string descriptor in `BX`, builds an FCB with INT 21h AH=29h and, if the name has no extension, fills in `EXE`.
2. Opens the file (AH=0Fh) and reads the 0x1A-byte MZ header (AH=27h random block read).
3. Computes the image size from the header and checks that it fits below the top of memory (otherwise it jumps to the runtime's error path).
4. Calls four runtime housekeeping routines (not decoded; presumably closing files and releasing resources), copies a small stub plus the header/FCB buffer to the top of memory and `retf`s into the stub.
5. The stub reads the rest of the image to the same load address as the running program, adds the load segment to every relocation entry, sets SS:SP and the entry CS:IP from the header, sets the DTA to PSP:0080h and `retf`s to the new entry point. On failure it prints `Error in EXE file`.

Chain call sites (BASIC string literal -> call of the loader):

| file | literal | target file | code offset |
|---|---|---|---|
| Gato.exe | `DEMO` | DEMO.EXE | 0xf3f |
| Gato.exe | `HISTORY` | History.exe | 0xf57 |
| Gato.exe | `GATO1` | Gato1.exe | 0xf74 |
| DEMO.EXE | `GATO` | Gato.exe | 0x829a |
| History.exe | `GATO` | Gato.exe | 0x356 |

`GATO1.EXE` contains no loader, no `GATO` literal and no reference to another executable, so once the game ends control cannot return to the menu: it ends the process (to DOS). *Inference from absence; the 'PLAY AGAIN? (Y/N)' prompt is handled inside the game.*

### 4.3 Menu dispatch in the launcher

The menu choice is stored in a numeric BASIC variable and compared with MBF constants [2.0, 3.0, 4.0] (DS offsets 0xf2e, 0xb90, 0xcc6) immediately before the chain calls:

```basic
IF CHOICE = 2 THEN CHAIN "DEMO"
IF CHOICE = 3 THEN CHAIN "HISTORY"
IF CHOICE = 4 THEN END
CHAIN "GATO1"            ' menu item 1 and any other key ("[1] NORMAL PLAY (DEFAULT)")
```

The menu text is in the launcher's literal pool: `[1] NORMAL PLAY (DEFAULT)`, `[2] DEMONSTRATION`, `[3] HISTORY AND SPECIFICATIONS`, `[4] EXIT`.

## 5. State passed between programs

| mechanism | evidence | verdict |
|---|---|---|
| BASIC `COMMON` variables | no `COMMON` string; the loader copies only 0x58, 0x20 words (stub, header/FCB buffer) and loads the new image at the same base as the running one; the new program's start-up code copies its own initial data image. The launcher's only variable of interest is the menu choice. Whether stale bytes of the old data segment survive in the new one was not determined | no hand-over found (not fully excluded) |
| command line / PSP | the loader keeps the original PSP (`DS=ES=PSP`, DTA reset to PSP:0080h); nothing in the launcher writes to it | PSP is shared but carries no GATO data |
| temporary/config file written by the launcher | the launcher's only file-name literals are `DEMO`, `HISTORY`, `GATO1`; none of the config/temp-file strings searched exists in any binary | none |
| DOS environment / registers | no INT 21h AH=4Bh, no environment access | none |
| persistent data files | `LOG1` is opened by the game and the demo with record length 32 (the `LOG` and `Log1` files in `Original/` are 2944 bytes = 92 x 32); the game-control parameters ([1] DIFFICULTY LEVEL; [2] SOUND; [3] TIME OF DAY; [4] RESET CAPTAIN'S LOG) are asked for *inside* `GATO1` after launch | state lives in `LOG1`, not in the launcher |

So the launcher is a pure program selector. The "configuration" screens belong to the game and the demo themselves.

## 6. Files each program references

| file | data-file / program literals (code offset of the load -> runtime routine called) |
|---|---|
| Gato.exe | `DEMO` -> 0x2767 (site 0xf3f); `HISTORY` -> 0x2767 (site 0xf57); `GATO1` -> 0x2767 (site 0xf74) |
| Gato1.exe | `LOG1` -> 0xd766 (site 0x998e); `ORDXX` -> 0xe5a2 (string concatenation) (site 0xbb66); `COURXX` -> 0xe5a2 (string concatenation) (site 0xbec3); `MXP` -> 0xd766 (site 0xc61f); `OBX` -> 0xe5a2 (string concatenation) (site 0xd018) |
| DEMO.EXE | `LOG1` -> 0x8412 (site 0x56fa); `DEMORD` -> 0x8412 (site 0x6de3); `MXP` -> 0x8412 (site 0x75f2); `OBX` -> 0x94a6 (string concatenation) (site 0x81e6); `GATO` -> 0xa912 (site 0x829a) |
| History.exe | `HISTORY` -> 0x11c6 (site 0x253); `GATO` -> 0x1bbf (site 0x356) |

The callee for `COURXX`, `OBX`, `ORDXX` is the runtime's BASIC string-concatenation routine (it adds the two lengths, checks for overflow and copies both strings). So these are *base names* that get a number appended at run time (`ORDXX` + n -> `ORDXX1`..`ORDXX20`, `COURXX` + n, `OBX` + n -> `OBX1`, `OBX3`..`OBX8`); `XX` is part of the name, not a placeholder. The other literals (`LOG1`, `MXP`, `DEMORD`, `HISTORY`) go straight to one shared routine per program, which I take to be the file-open routine (inferred from usage: it also receives the record length for `LOG1`). `DEMO` reads `DEMORD` instead of `ORDXX`/`COURXX`, so its scenario is scripted rather than loaded.

## 7. Other observations

* `Gato.exe` is the only binary with the start-up memory check text (`fail in 64k boundary fixup`, `Insufficient memory` at 0x67f2); the three chain-loaded programs do not have it, which fits the design that only the launcher is started by DOS.
* `Gato1.exe` and `DEMO.EXE` hold the same 48-value numeric `DATA` text (12 records of x, y, size, aspect) that probably draws the islands on the chart screen; `Gato1.exe` ends with the unexplained text `POUET`.

## 8. Confidence and open questions

* **Certain** (read from code/bytes): header facts, no packing, the FCB-only DOS API, the loader routine and its call sites, the 2/3/4 menu constants, the absence of COMMON/config strings.
* **Strong inference**: `GATO1` terminates to DOS (no loader/`GATO` literal); `LOG1` is the only cross-session state; the three chain-loaded programs are never started from DOS by design.
* **Unknown**: exact compiler release; whether the runtime re-initialises *all* variables on chain or leaves some bytes from the previous program in memory (not exploited by any code path found); what `POUET` is.
